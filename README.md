# РБПО — лабораторная работа №4

**Вариант 27. Редакция новостного издания**

Java 21 · Spring Boot 3.5.5 · Spring Security · Spring Data JPA · PostgreSQL 16 · Flyway · Maven

## Назначение приложения

Проект является продолжением лабораторной работы №3. Существующая предметная область редакции новостного издания, PostgreSQL, пять основных сущностей, REST CRUD API и пять редакционных бизнес-операций сохранены. Добавлены HTTP Basic Authentication, CSRF-защита, регистрация пользователей, хранение BCrypt-хешей паролей и разграничение доступа по ролям и состоянию учётной записи.

## Аутентификация

Для каждого защищённого API-запроса используется HTTP Basic Authentication. Учётные записи загружаются из таблицы `app_users` через `DatabaseUserDetailsService`. Пароли хранятся только в виде BCrypt-хешей. В конфигурации используется `BCryptPasswordEncoder` с фактором 10. Контекст аутентификации не сохраняется в HTTP-сессии: Basic Auth повторно проверяет актуальное состояние учётной записи при каждом запросе. HTTP-сессия используется отдельно для хранения CSRF-токена.

Демо-учётные записи, создаваемые миграцией `V3`:

| Логин | Пароль | Роль | Состояние |
|---|---|---|---|
| `chief_editor` | `EditorDemo!2026` | `EDITOR` | `ACTIVE` |
| `journalist_ivan` | `JournalistDemo!2026` | `JOURNALIST` | `ACTIVE` |
| `journalist_anna` | `JournalistDemo!2026` | `JOURNALIST` | `ACTIVE` |

Эти пароли предназначены только для локальной демонстрационной базы. Для реальной эксплуатации их необходимо заменить.

## CSRF-защита

CSRF-защита включена для всех изменяющих состояние HTTP-методов (`POST`, `PATCH`, `PUT`, `DELETE`). Приложение использует `HttpSessionCsrfTokenRepository`. Для получения токена отправьте публичный запрос:

```http
GET /api/auth/csrf
```

Ответ содержит `headerName`, `parameterName` и `token`. Для последующих запросов изменения передавайте полученное значение в заголовке `X-CSRF-TOKEN`. Клиент должен сохранять cookie сессии `JSESSIONID`, поскольку токен связан с серверной сессией.

Регистрация доступна без Basic Auth, но также требует CSRF-токен. GET-запросы не требуют CSRF-заголовка.

## Регистрация и состояние учётной записи

Регистрация: `POST /api/auth/register` с полями `username`, `displayName`, `email`, `password`. Проверяется уникальность имени и email без учёта регистра. Пароль должен содержать от 12 до 72 байт UTF-8, строчные и прописные латинские буквы, цифру и специальный символ.

Сервер всегда назначает новой учётной записи роль `JOURNALIST` и состояние `ACTIVE`. Роль из запроса регистрации не принимается, поэтому пользователь не может самостоятельно зарегистрировать редакторскую учётную запись.

Состояния аккаунта:

- `ACTIVE` — аутентификация разрешена;
- `LOCKED` — вход блокируется из-за временной блокировки;
- `DISABLED` — вход отключён.

Учётная запись, созданная редактором через CRUD `POST /api/users`, получает случайный недоступный пользователю пароль и состояние `DISABLED`. Редактор может назначить ей пароль через `PATCH /api/users/{id}/password`; применяется та же политика надёжности, пароль хешируется BCrypt, после чего запись переводится в `ACTIVE`. Редактор может менять состояние аккаунта через `PATCH /api/users/{id}/account-status` с JSON-телом `{"accountStatus":"LOCKED"}`, `{"accountStatus":"ACTIVE"}` или `{"accountStatus":"DISABLED"}`. При блокировке или отключении пользователя последующие Basic Auth запросы отклоняются с `401 Unauthorized`.

## Роли и правила доступа

В проекте определены две роли:

| Возможность | `EDITOR` | `JOURNALIST` |
|---|---:|---:|
| Просмотр статей, рубрик и выпусков | Да | Да |
| CRUD рубрик | Да | Нет |
| CRUD пользователей и управление состоянием аккаунта | Да | Нет |
| CRUD редакторских проверок | Да | Нет |
| Создание и управление выпусками | Да | Нет |
| Создание статьи | Любому автору | Только от своего имени |
| Изменение и удаление статьи | Любой статьи | Только собственной неопубликованной статьи |
| Отправка собственной статьи на проверку | Да | Да |
| Одобрение и возврат статьи на доработку | Да | Нет |
| Включение статьи в выпуск и публикация выпуска | Да | Нет |

Роль проверяется через `SecurityFilterChain` и `@PreAuthorize`. Проверка владельца статьи учитывает текущего пользователя и автора, указанного в запросе. Журналист не может подменить автора своей статьи или отправить на проверку чужой материал.

## Обработка отказов

- `401 Unauthorized` — отсутствующие, неверные учётные данные или заблокированная/отключённая учётная запись. Ответ не раскрывает, существует ли конкретный логин.
- `403 Forbidden` — пользователь аутентифицирован, но не имеет необходимых полномочий, либо CSRF-токен отсутствует/неверен.
- `400 Bad Request` — неверный формат запроса или пароль не соответствует политике регистрации.
- `404 Not Found` — запрошенная сущность не найдена.
- `409 Conflict` — конфликт уникальности, нарушение целостности или недопустимый переход бизнес-состояния.

Ответы об ошибках используют единый JSON-формат `ApiError`. В них не включаются пароли, хеши паролей, stack trace или внутренние детали аутентификации.

## REST API и бизнес-операции

Все CRUD-маршруты лабораторной №3 сохранены. Редакционные бизнес-операции также сохранены: отправка статьи на проверку, одобрение, возврат на доработку, включение статьи в выпуск и публикация выпуска. Правила ролей дополняют ограничения бизнес-состояний: роль `EDITOR` требуется для редакторских решений и публикации, а `JOURNALIST` может отправить на проверку только собственную статью.

Идентификация текущего пользователя доступна по маршруту `GET /api/auth/me`.

## База данных и миграции

Используется PostgreSQL 16. Миграция `V3__add_authentication_and_authorization.sql` добавляет в `app_users` поля `password_hash`, `role`, `account_status`, назначает демо-ролям значения и записывает BCrypt-хеши демо-паролей. Предыдущие миграции `V1` и `V2` не изменяются.

Для запуска используется локальный `.env`, файл исключён из Git. Шаблон находится в `.env.example`. Пароль приложения БД не следует публиковать.

## Запуск

1. Создайте `.env` из шаблона:

   ```powershell
   Copy-Item .env.example .env
   ```

2. Укажите параметры подключения к PostgreSQL в `.env`.
3. Если PostgreSQL запущен локально, убедитесь, что база `news_editorial_db` и пользователь `news_app` существуют и имеют права на схему `public`. Либо используйте Docker Compose:

   ```powershell
   docker compose up --build -d
   ```

4. Для запуска из IntelliJ IDEA откройте `pom.xml`, дождитесь импорта Maven и запустите `RbpoLab4Application`. Приложение выполнит миграцию V3 при первом старте.
5. Базовый адрес API: `http://localhost:8080`.

## Коллекция Postman

Файл `postman/RBPO_Lab4_Variant27.postman_collection.json` содержит запросы для регистрации, CSRF, идентификации, позитивных и негативных сценариев аутентификации/авторизации, CRUD пяти сущностей и пяти бизнес-операций. Запускайте запросы в порядке папок сверху вниз: сначала получите CSRF-токен, затем выполните регистрацию/проверку ролей, после этого CRUD и редакционный workflow. Postman должен сохранять cookie jar между запросами.

Демо-переменные коллекции `editorUsername`, `editorPassword`, `journalistUsername`, `journalistPassword` соответствуют локальным демо-учётным записям миграции. Пароль регистрации `registrationPassword` предназначен для демонстрационного сценария. Имена нового зарегистрированного пользователя формируются с временным суффиксом, чтобы можно было повторять сценарий.

## Тестирование

Запуск тестов:

```powershell
mvn clean test
```

`RbpoLab4IntegrationTest` проверяет CRUD и бизнес-логику без web security filters, используя роль редактора для тестового контекста. `SecurityIntegrationTest` запускает реальные Spring Security filters и проверяет HTTP Basic Auth, регистрацию, BCrypt, CSRF, роли, доступ к собственным статьям и блокировку учётной записи. Для тестового профиля используется H2 в режиме совместимости с PostgreSQL; отдельный запуск приложения с профилем по умолчанию подключается к реальному PostgreSQL.
