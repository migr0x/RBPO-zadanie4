## Сборка и автоматические тесты

Среда проверки: Windows, Java 25.0.2 (целевой Java release проекта — 21),
Maven 3.9.16, Spring Boot 3.5.5, PostgreSQL 16.15.

- `mvn clean verify`: успешная сборка исполняемого JAR и первоначальный набор
  из 49 тестов, без ошибок и пропусков.
- После добавления проверок срока сессии в БД, владельца сессии и Bearer POST
  выполнен `mvn test`: **52 теста, 0 failures, 0 errors, 0 skipped**.
- Из них 21 проверка JWT, 16 интеграционных проверок токенов/сессий и
  15 сохранённых проверок CRUD, бизнес-операций и безопасности работы №4.

Проверены подпись HS256 и отказы для подменённых, неподписанных и HS512-токенов;
обязательные `sub`, `jti`, `iat`, `exp`, `type`; истечение без допуска после
`exp`; уникальность `jti`; секундная точность сроков в JWT и БД; разделение
access/refresh; регистрация без повышения роли; ошибки обязательных полей;
отключённые, заблокированные и удалённые пользователи; неизвестные сессии;
несоответствие владельца; запрет refresh по истёкшему сроку записи БД.

Проверены сохранение `REVOKED` при HTTP 401, откат регистрации при ошибке
сохранения сессии, откат `USED` при ошибке сохранения новой пары, а также
два одновременных refresh-запроса: ровно один успешный обмен и один отказ.
Refresh успешно работает без access, с просроченным access и с некорректным
Bearer-заголовком. Защищённый POST с access работает без CSRF, при этом
прежние проверки Basic/CSRF проходят.

## Проверка на PostgreSQL

Для проверки поднят отдельный локальный кластер PostgreSQL на
`127.0.0.1:55435` с отдельной БД `lab5_validation`. Исходная база работы №4
для проверок не использовалась. Приложение запускалось обычным профилем
на `http://127.0.0.1:18085` из собранного JAR.

- Flyway успешно применил миграции V1–V4; Hibernate проверил схему.
- Под сервисной ролью `news_app` подтверждены права `SELECT`, `INSERT`,
  `UPDATE` на `public.user_sessions`; роль не является суперпользователем.
- Все **16** `TokenSessionIntegrationTest` дополнительно выполнены против
  PostgreSQL с включённым Flyway и `ddl-auto=validate`: **0 ошибок**.
  Это включает конкурентный обмен, сохранение отзыва после отказа и откаты.

Для повторения на собственной отдельной тестовой PostgreSQL-БД:

```powershell
mvn "-Dtest=TokenSessionIntegrationTest" `
  "-Dspring.datasource.url=jdbc:postgresql://localhost:5432/lab5_test" `
  "-Dspring.datasource.username=news_app" `
  "-Dspring.datasource.password=$env:DB_PASSWORD" `
  "-Dspring.datasource.driver-class-name=org.postgresql.Driver" `
  "-Dspring.jpa.hibernate.ddl-auto=validate" `
  "-Dspring.flyway.enabled=true" test
```

## HTTP-коллекция Postman

Выполнено против работающего приложения с PostgreSQL:

```powershell
postman collection run postman/RBPO_Lab5_Variant27.postman_collection.json --env-var "baseUrl=http://127.0.0.1:18085" --no-report-events
```

Результат: **23 запроса, 80 assertions, 0 ошибок**, код завершения 0.
Для основного workflow SQL подтвердил две строки с одной меткой устройства:
одну `REVOKED` и одну `ACTIVE`. Дополнительной строки после повторного
использования старого refresh нет. Регистрация проверяется отдельной цепочкой.

Проверки хранятся в коллекции и тестах. Секреты из локального `.env`, выданные
токены и журналы HTTP-ответов в Git не добавлены. Экспорт `--output` не
использовался: установленный Postman CLI ограничивает его Enterprise-тарифом;
итоговый результат получен из обычного локального прогона без экспорта.
